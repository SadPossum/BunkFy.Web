# Reservation creation: same-tab recovery

Calendar direct-booking R2 uses the existing create operation ID as reservation ID, as implemented by the backend creation handler. This is not a new API or a guarantee of cross-device recovery.

Before sending a new reservation POST, the frontend confirms a write and exact readback of `bunkfy.reservation-create-recovery.v1` in sessionStorage. The strict versioned value contains only tenant ID, actor subject ID, authenticated session ID, property ID, operation/reservation ID, state, a boolean optional-guest-follow-on flag, and creation/update timestamps. No token, username, guest fields, selected inventory, request payload or payload fingerprint is persisted. The full payload and exact-replay fingerprint stay in the mounted form only.

The coordinate moves from `prepared` to `primary-confirmed`, then `follow-on-unknown` while optional guest creation/linking is unresolved, or `complete`. It is retained while the new form or asynchronous follow-on owns the work. The matching existing detail route is the `handed-off` boundary; only then is the marker cleared. Failed writes or removal are visible and do not authorize an untracked fresh create.

On reload/remount, the current stable tenant, subject and authenticated session must match, the exact property must be accessible and selected, and current `reservations.read` evidence is required. Recovery makes a cancellable existing property-scoped GET by operation ID. A matching positive-version receipt opens the existing reservation, never another POST. Known current room topology plus exact returned property/unit/stay validates an unchanged Calendar target; unproved or malformed origin uses generic scoped detail. Optional guest creation/linking is not automatically repeated or claimed successful by primary existence alone.

404 can race a still-finishing POST. 401/403, 503, offline, abort, malformed/mismatched receipt and changed authority do not prove the save failed. The marker is retained, with explicit recheck and reservation-directory actions. There is no background recovery poll and no silent timeout expiry. Same-mounted unchanged POST retry retains its exact operation and payload; editing fields cannot silently discard an unresolved operation.

An operator can deliberately remove an unreadable, foreign-session or unresolved marker after acknowledging that removal neither cancels the reservation nor proves its absence; creating again can duplicate it. No foreign-session lookup is made. A pending dispatch cannot be abandoned. Storage policy that prevents confirmed sessionStorage must be resolved before a fresh create; do not bypass it through an untracked fallback. Do not log marker values or include them in ordinary analytics.

This is a bounded same-tab promise. Closed tabs, a new authenticated session, another device and other tabs are support boundaries, not recovered drafts. Browser restore/duplicate-tab behavior may retain a coordinate but does not restore guest fields. Operators should inspect the exact property directory or ask staff with read authority before manually creating again. Opaque metadata is still personal-data-adjacent; retention/support/privacy policy needs owner review.

Rollback must not automatically delete this versioned key. An older client may ignore it but cannot promise this recovery behavior; retain the recovery-capable client or use deliberate supported reconciliation before further creation. This local frontend implementation does not close exact-commit CI, hosted operational controls, security/legal admission, representative human or assistive-technology testing.
